# v1.1: multiple tuners and patch downgrade compatibility

Status: development started; runtime implementation and Plex validation are outstanding. The foundation change adds release-line controls and the compatibility specification. It does not claim that multiple tuners or patch downgrades already work.

Baseline: v1.0.4 (`e1fdf4bc738e0a39c1b83a9f1f3c8148bb6758f4`), retaining the v1.1.0-alpha.1 version and 1.1 release line. Preserve its stricter service/country/station matching, updated channel aliases, and delayed-audio startup handling throughout the multi-tuner refactor.

## Agreed scope

1. Multiple independently enabled Plex tuner devices, with editable channel presets and guide-location recommendations. The only initial preset is **USA - New York City**, using the current channel lineup. Other locations will be set up later; London and Los Angeles are future examples, not launch presets.
2. In-place downgrade compatibility between stable 1.1 patch releases, starting at 1.1.0. See [the versioning contract](VERSIONING.md).

Keep the current `/data` directory. A 1.0 → 1.1 upgrade can migrate its internal schema; returning to 1.0 requires a pre-upgrade backup. This replaces the earlier idea of keeping the expanded catalogue readable by 1.0. Do not build a duplicate legacy catalogue just to support cross-minor downgrades.

## Automatic data upgrade

The first 1.1 startup must automatically detect and convert supported older data to the new tuner-aware format, before listeners, matching, recruitment, or cleanup start. No manual export/import or intermediate app installation is required. Reuse the existing primary tuner identity and attach existing channel IDs, rules, policies, mappings, and rosters to it; retain accounts, credentials, settings, and login. Preserve an intentionally empty lineup instead of reseeding it.

Use ordered, versioned migrations with validation and transactional database changes. Update the format marker only after a successful migration. For configuration changes outside SQLite, stage and recover the complete operation across crashes. A failed or interrupted conversion must leave recoverable data and safely retry; unknown/newer formats must stop startup with a clear explanation. Never fall back to creating an empty catalogue after an error.

Before releasing 1.1, test direct upgrades from every published stable 1.0 data format, including customised and empty lineups, missing optional metadata, and interrupted migrations. The published Beta 3 and v1.0.4 fixtures are the initial harness, not evidence that the future schema migration is already implemented. Also test reopening already-migrated data: it must not duplicate tuners, reset edits, or change identities.

## Tuner and channel model

- Preserve the existing primary profile ID, HDHomeRun DeviceID, tuner address, channel IDs, and all user edits. Present the existing tuner as **USA - New York City** without resetting its channels. Do not infer that every existing customised lineup is actually New York; retain/allow correction of market metadata.
- New York is optional, like every other tuner. Upgrades retain the existing tuner and its enabled channels; fresh installations offer the preset for selection. Users can disable or explicitly remove it. An installation with no enabled tuners is valid and must not silently recreate New York after a restart or update. Keep the legacy primary ID reserved: adding a tuner must never silently give it a removed device's identity.
- Give each added tuner an immutable profile ID and unique, persistent HDHomeRun identity. Names, enabled state, country, market, IANA time zone, and guide recommendations are editable metadata, not identity.
- A channel belongs to a tuner and has a globally unique permanent internal ID. Channel numbers are unique within their tuner, not globally. Initially, channel definitions, matching rules, exclusions, policies, and rosters are independent between tuners so editing one tuner never changes another silently.
- Refactor the existing `output_profiles`/`output_assignments` foundation into one coherent model. Remove the unconditional primary-channel triggers and global number constraint in a transactional migration. Avoid two competing sources of truth for channel presentation or enabled state. Choose the exact schema after the Plex prototype and migration design review.
- Keep accounts, source metadata, upstream budgets, provider pacing, and the streaming engine shared. Scope matching resolution to the tuner while retaining the existing checks for recognised conflicting services, countries, and station IDs.
- Within a tuner, viewers of the same channel continue sharing one controller. Do not key playback by channel number. Cross-tuner media sharing is deferred until identical service and rule semantics can be established.
- Disabling a tuner retains its definitions, blocks new tunes, and stops unnecessary recruitment. Existing sessions may finish. Removing a tuner is a separate confirmed action scoped to that tuner.
- Keep global viewer/upstream limits authoritative across all tuners. `TunerCount` describes concurrent capacity, not the number of profiles. Define per-device advertised capacity and prove that Plex scheduling and admission agree rather than multiplying the existing global limit per device.

## Plex integration gate

Prototype two distinct virtual devices before committing to routing or the complete UI. Test separate stable ports first, retaining the primary address. Test path-prefixed endpoints only as an alternative; do not assume Plex preserves the path. Account for Docker port publishing and the existing stream-only fallback. New listeners must remain off the public administration surface.

Using the actual supported Plex version, verify:

- At least two devices with distinct identities and independent guide selection. Use disposable custom lineups to exercise different countries and markets; this does not require shipping additional presets.
- Overlapping channel numbers, including simultaneous viewing and scheduled recordings.
- Device and guide identity after restart, rename, disable/re-enable, and an app upgrade.
- Correct affiliate/regional feeds under primary-to-backup failover.
- Per-device discovery/lineup responses, capacity limits, and fallback routing.

HTTP tests alone do not establish these behaviours. Record the tested Plex version and remaining limitations. No preset should claim a verified guide recommendation without checking the actual country/postal-code/lineup selection. Guide metadata does not prove what a provider is broadcasting.

## Output page

Shared resource limits and default policies remain above the tuner sections. Each tuner is an accessible expandable section containing its enabled state, connection address, guide recommendation, channels, roster summaries, and channel add/edit/remove controls. Preserve expanded state during refresh and fetch roster detail lazily.

Place **Add tuners** as an expandable section at the bottom. Show available presets with names, channel counts, guide recommendations, and an Add action. Presets are versioned data copied on addition, never live templates that overwrite user edits when Antennarr updates. Prevent accidental duplicate addition while preserving the ability to build a custom tuner later.

Initially this section contains only **USA - New York City**. Show whether it is already added; disabling it does not add a second copy. Removing it makes the preset available again, but re-adding creates a new device identity and must explain that Plex needs configuring again. Do not display unavailable locations as selectable tuners.

Scope lineup import/export, clear, and reset-to-preset actions to the selected tuner. Legacy API routes must retain their documented primary-tuner meaning; add explicit profile routes for new operations. Portable presets/lineups contain no source credentials or exported device identity. Full backups retain all device identities and user state.
